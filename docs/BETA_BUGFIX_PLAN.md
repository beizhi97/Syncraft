# Beta 缺陷修复计划

本文记录进入 Beta 前确认的缺陷、修复状态和剩余产品化工作。当前运行时合同仍以 `docs/INTERFACE_CONTRACT.md` 为准。

## SFSC-BETA-PROGRESS-001：同步总量在传输过程中持续增长

- 严重级别：P2（进度展示异常）
- 状态：`0.2.0-beta.2` 已实现，待发布验收
- 发现日期：2026-07-13
- 影响范围：客户端上传、下载、镜像同步和双向同步的进度展示

### 用户现象

同步已经进入传输阶段后，“已传输”右侧的总量仍持续增长，例如从较小值逐步增加到 `5.589 GiB` 或更大，导致进度百分比可能倒退、ETA 跳变。界面目前没有说明该分母只是 rclone 已发现的待传数据量，用户会把它理解为任务开始前已经确认的最终总量。

### 已确认根因

1. 当前 `buildRclonePreview` 为 rclone 生成 `-P --stats=1s`，但没有使用 `--check-first`。
2. rclone 的 `copy`、`sync` 和相关传输默认在目录检查尚未完成时尽快开始传输；统计中的 `totalBytes` 会随着新文件进入待传队列而增长。
3. `client/src/rcloneStats.js` 正确解析了每次 rclone 输出，但 `client/src/clientServer.js` 会用最新 `totalBytes` 覆盖当前指标。
4. `client/public/app.js` 直接把该动态分母显示在“已传输”一栏，没有区分“扫描中”和“传输计划已确认”。

这不是 GiB 单位换算错误。主因是执行阶段没有先封口传输计划，同时 UI 把动态发现量展示成了最终总量。

### 受控复现证据

使用客户端打包内的 rclone `v1.74.3`，对 6000 个、合计 `5.859 MiB` 的本地测试文件执行相同复制任务，并用 `--max-backlog 1` 放大默认边扫描边传输行为：

- 未使用 `--check-first`：4 秒内观察到 40 个不同总量，分母从 `13 KiB` 持续增长到 `403 KiB`。
- 使用 `--check-first`：传输阶段只观察到一个总量，固定为 `5.859 MiB`。

解析器回放测试也能稳定复现：当连续 rclone 状态的分母从 `5.589 GiB` 增长到 `6.200 GiB` 时，客户端当前状态会无条件采用后一个值。

### 目标行为

1. 用户点击开始后，任务先进入“扫描中/正在计算总量”阶段。
2. 扫描阶段不显示未经确认的百分比、最终总量或 ETA。
3. 传输开始前完成源端枚举和目标差异检查，形成该轮传输基线。
4. 进入“传输中”后，总文件数和总字节数保持稳定，进度百分比不得因继续发现普通待传文件而倒退。
5. 如果源文件在扫描后新增、增长或改变，显示“源内容已变化，需要重新计算”或明确的计划变更提示，不得静默扩大总量。
6. 失败重试产生的额外传输量与原始计划总量分开展示，不得把重试流量伪装成新增文件总量。
7. 无需传输的任务应从扫描阶段直接进入“已完成”，并显示 `0 B / 0 B` 或“内容已是最新”。

### 修复步骤

1. 先增加失败回归测试，覆盖连续统计分母增长、百分比倒退和 UI 误标最终总量。
2. 为同步指标增加明确阶段：`scanning`、`transferring`、`verifying`、`completed`；如该字段进入 heartbeat，则同步更新协议文档、schema 和合同测试。
3. 对 `copy`、`sync`、`bisync` 候选命令验证并启用 `--check-first`，传输阶段开始后锁定本轮计划总字节数和文件数。
4. UI 在扫描阶段显示不确定状态；只有传输基线锁定后才显示 `已传输 / 总计`、百分比和 ETA。
5. 识别基线锁定后的总量变化，区分源目录变化、失败重试和解析异常，并给出稳定状态或错误码。
6. 检查 `--check-first` 将待传对象保存在内存中的成本，对 1 万、10 万及更大文件集执行内存和启动耗时测试；超过产品边界时给出明确限制或采用可落盘的预扫描方案。
7. 重建客户端 EXE，执行全量合同测试、桌面包 smoke 和真实 N1 上传/下载/双向同步验收。

### 验收标准

- 扫描期间 UI 明确显示“正在计算总量”，不显示会被误解为最终值的分母。
- 在源目录静止且无失败重试的情况下，传输开始后的 `totalBytes` 和 `totalObjects` 不再增长。
- 进度百分比在同一传输阶段单调不减，并最终到达 100%。
- 上传、下载、普通 copy、危险镜像 sync、首次 bisync 和后续 bisync 均有回归覆盖。
- 同步期间新增或修改源文件时，UI 显示计划变化状态，而不是静默修改最终总量。
- 大文件数量场景的峰值内存和扫描耗时有测试报告，满足 Beta 主机最低配置。

### 临时说明

修复前该分母只能理解为“当前已发现的待传总量”，不是任务最终总量。它变大不代表重复上传，也不能单独证明源文件发生变化。

## SFSC-BETA-CONFLICT-001：单向上传把文件名误判为同步冲突

- 严重级别：P2（错误分类和诊断信息错误）
- 状态：`0.2.0-beta.2` 已实现，待发布验收
- 发现日期：2026-07-13
- 影响范围：客户端 rclone 输出解析、同步历史、顶部状态、心跳摘要和错误恢复提示

### 用户现象

对新目标执行“上传（本地 -> 远端）”后，客户端显示“有冲突 328 项”，并提示用户暂停双向同步。该任务实际是单向 `copy`，远端是否为空都不应产生产品定义中的双向文件冲突。历史记录同时显示 rclone 退出码 `1`，但 UI 优先展示了冲突提示，隐藏了真正的传输失败原因。

### 已确认根因

1. `client/src/rcloneStats.js` 只要在任意 rclone 输出行中发现单词 `conflict` 或 `bisync`，就创建一个冲突事件；它不判断任务方向，也不验证该行是否为真实的 bisync 冲突事件。
2. 因此普通文件路径中的 `.sync-conflict-...`、目录名中的 `conflict`、HTTP `409 Conflict` 或其他普通错误文本都会被误判。
3. 同一个文件会在 rclone 每秒进度输出中重复出现。解析器和 `mergeConflictSummary` 按日志出现次数累加，而不是按真实冲突事件或文件去重，所以少量文件可被膨胀成数百项。
4. `client/public/app.js` 只要看到 `run.conflicts.count > 0`，就把历史状态、徽标和详情优先显示为“有冲突”，即使任务方向是上传/下载且 `status: error`、`errorCode: rclone_sync_failed`、`exitCode: 1`。

### 现场证据

- N1 的 `home-sync/devices/test1` 中找到 24 个文件名包含 `.sync-conflict-...` 的对象。这些是源目录中既有的 Syncthing 冲突副本文件名，不是 SFSC 本轮检测出的冲突。
- 这些对象元数据写入时间为本轮上传期间的 2026-07-13 14:39 至 14:46，不能据此认定 MinIO 在任务开始前已有这些对象；“服务器全新”与误报无关。
- 解析器回放普通上传错误和一个带 `conflict` 的文件路径，会错误产生 2 项冲突。
- 将同一条真实冲突样例日志重复 328 次，当前解析结果为 `count: 328`，但 `files[]` 只有同一个文件，证明计数会被重复进度/日志行放大。

### 尚未确认的独立问题

截图中的 rclone 退出码为 `1`，说明本轮上传仍有一个真实失败。误报冲突不会让 rclone 自己返回退出码 `1`。由于截图对应客户端当前不在本机运行，无法读取该轮原始 `rclone.log`，因此不能从现有证据判断真实失败属于源文件变化、文件读取失败、S3 请求错误、路径问题或其他原因。

修复后必须保证这类真实错误不会再被冲突提示遮蔽，并在同步历史和诊断包中保留脱敏后的首个/最后一个有效 rclone 错误摘要。

### 目标行为

1. 只有双向 `bisync` 任务可以产生 SFSC “同步冲突”状态；上传、下载和镜像任务不得进入该状态。
2. 文件名或目录名包含 `conflict`、`.sync-conflict-*` 时，必须按普通文件处理。
3. HTTP 状态文本 `409 Conflict`、普通错误说明和命令说明文本不得被当作文件冲突。
4. 真实 bisync 冲突必须从明确、可验证的 rclone 事件模式中识别，并按规范化文件路径/事件 ID 去重。
5. 同一真实冲突在多次进度刷新或重试日志中出现时只计一次。
6. `status: error` 时，UI 必须优先显示稳定错误码、退出码和脱敏错误摘要；真实冲突作为附加信息，不得替代失败原因。
7. 对旧的单向同步历史记录，展示层应忽略或迁移清除不可能成立的 legacy `conflicts` 数据。

### 修复步骤

1. 先增加失败回归测试：单向任务中的 `.sync-conflict-*` 文件、路径包含 `conflict`、HTTP `409 Conflict`、重复日志行和退出码 `1` 被冲突提示遮蔽。
2. 让冲突解析器接收任务方向；非 `bidirectional` 方向直接禁用冲突识别。
3. 用真实 rclone bisync 输出样本定义严格事件模式，替换当前宽泛的 `/\b(conflict|bisync)\b/i` 匹配。
4. 按规范化冲突文件路径和事件类型去重，计数表达唯一冲突数量，不表达日志出现次数。
5. 调整历史列表、顶部状态和详情的优先级：运行失败优先，真实冲突其次；恢复建议必须与任务方向一致。
6. 在进程运行期间保存脱敏、限长的 rclone 错误摘要到 `lastRun`；诊断包继续执行路径和凭据脱敏。
7. 读取旧历史时修正单向任务中的伪冲突，并保证服务端 heartbeat/管理摘要不会继续传播这些错误数据。
8. 使用包含真实 `.sync-conflict-*` 文件名的目录对 N1 执行上传回归，并另行制造一个真实 bisync 冲突验证正例。

### 验收标准

- 空远端和非空远端的单向上传/下载都不会显示“同步冲突”。
- 1000 个名称包含 `conflict` 的普通文件可以正常同步，冲突计数仍为 0。
- 同一 bisync 冲突在任意次数的重复进度输出中只计一次。
- 两端同时修改同一文件时，真实 bisync 冲突仍能稳定识别、展示并进入诊断摘要。
- rclone 退出码非 0 时，用户首先看到真实失败类型和可执行建议，不会看到与任务方向不符的“双向同步”提示。
- 既有单向历史中的伪冲突不再污染顶部状态、客户端心跳或服务端设备摘要。

### 临时说明

修复前，单向任务里显示的“冲突数量”不可信。遇到此状态应以 rclone 退出码和原始脱敏日志为准，不要按界面提示执行双向冲突处理。

## SFSC-BETA-ENDPOINT-001：N1 内部端点泄漏到 SyncKey 和客户端 UI

- 严重级别：P2（架构耦合、可迁移性和用户信任问题）
- 状态：`0.2.0-beta.2` 已完成兼容性整改；受管本地转发保留为后续协议演进
- 发现日期：2026-07-13
- 影响范围：N1 部署模板、服务端存储状态、SyncKey profile、客户端 rclone 配置、远端目标摘要和后续服务器迁移

### 用户现象

客户端远端目标中显示 `http://n1-minio.sfsc:9000`，但用户从未创建、授权或配置该地址。该名称看起来像未知网络端点，无法从 UI 判断它是否属于当前服务器，也无法解释数据是否会发送到第三方。

### 已确认来源

1. `server/docker-compose.n1.yml` 人为固定了 `S3_CLIENT_ENDPOINT=http://n1-minio.sfsc:9000`，并通过 `extra_hosts` 在服务端 sing-box 容器内把 `n1-minio.sfsc` 映射到 `127.0.0.1`。
2. N1 的 MinIO 只监听宿主机 `127.0.0.1:9000`；该名称不是公网 DNS，也不是第三方服务，作用是让经 VLESS/REALITY 隧道到达的客户端请求转到 N1 本机 MinIO。
3. 服务端读取 `S3_CLIENT_ENDPOINT` 后把它写入 `profile.storage.endpoint`；客户端兑换 SyncKey 后原样派生为 job 的 `s3Endpoint`，最终写入 rclone 配置并显示在远端目标摘要中。
4. 当前 N1 持久化状态中的 `endpoint` 和 `internalEndpoint` 都是 `http://n1-minio.sfsc:9000`，但运行环境规定服务端内部地址应为 `http://minio:9000`，已经存在客户端端点和服务端内部端点混用的状态漂移。

该地址能够工作，但它是开发阶段引入的 N1 专用实现细节，不是用户配置，也不应成为用户需要理解或授权的同步任务字段。

### 设计问题

- N1 专用主机名进入 SyncKey 和持久化 job，导致 profile 与具体部署环境耦合。
- 服务器迁移、网络结构调整或移除 N1 后，旧 SyncKey/profile 可能失效。
- 客户端端点和服务端内部端点语义不清，状态文件可能保存错误值并依赖运行时 fallback 才能工作。
- 普通 UI 暴露底层地址，用户无法验证其归属，损害产品信任。
- `sync.970506.xyz` 作为产品公网身份与另一个未经配置的 `.sfsc` 名称同时出现，增加理解和排障成本。

### 目标架构

用户只需要认识：

```text
服务地址: sync.970506.xyz
同步标识: 同步 ID
本地目标: 用户选择的文件夹
```

底层职责应分离为：

```text
客户端 rclone -> 客户端本机受管转发端口
客户端 sing-box -> VLESS/REALITY 隧道
服务端 sing-box -> 服务端内部 MinIO 服务
服务端内部 MinIO -> http://minio:9000
```

- 新 SyncKey/profile 不再暴露 N1 专用主机名；存储连接应使用版本化的服务描述或本机受管转发信息，而不是用户可见的原始基础设施地址。
- rclone 应只连接客户端本机受管端点，例如 `http://127.0.0.1:<managed-storage-port>`；该端口由客户端运行时和 sing-box 配置共同管理，不允许用户手工填写。
- 服务端独占知道 `http://minio:9000` 等内部服务地址，MinIO 不直接暴露公网。
- 普通 UI 只显示存储连接状态、同步 ID 和逻辑目标；原始端点仅可出现在受控高级诊断中，并应明确标注为内部路由。
- 服务端状态必须明确区分 control-plane/internal endpoint 与 client transport，不再让一个 `endpoint` 字段承担两种语义。

### 迁移步骤

1. 为本机受管存储转发做技术验证，确认 Windows 客户端、sing-box、rclone、停止/重启和多任务场景下端口生命周期稳定。
2. 先修正服务端存储状态模型，将内部 MinIO 地址和客户端传输描述拆分，并迁移 N1 当前漂移状态。
3. 设计向后兼容的 profile 扩展，例如版本化 `storage.transport`；Protocol v1 继续读取 legacy `storage.endpoint`，新客户端优先使用受管传输描述。
4. 客户端生成本地转发配置，rclone 只使用 loopback 受管端点；验证该端点不会因 `NO_PROXY` 或代理配置绕过 sing-box。
5. 从普通同步任务 UI 移除“端点”；高级诊断只显示连接模式和脱敏目标，不显示用户不可操作的 N1 专用名称。
6. 新签发 SyncKey 停止携带 `n1-minio.sfsc`。旧 SyncKey/profile 在兼容窗口内继续工作，并提供重新签发/重新导入迁移路径。
7. 完成客户端覆盖率和旧 profile 迁移率检查后，再移除 N1 compose 中的 `S3_CLIENT_ENDPOINT` 和 `extra_hosts` 兼容别名。
8. 迁移和回滚必须分别经过 N1 与 `sync.970506.xyz` 目标服务器的真实上传、下载和断网恢复验证。

### 验收标准

- 新签发 SyncKey/profile、保存的 job 和普通客户端 UI 中不再出现 `n1-minio.sfsc`。
- 用户无需配置、批准或理解 MinIO endpoint；客户端只展示同步 ID 和连接状态。
- rclone 只连接本机受管存储端点，抓包和进程参数验证数据仍经 sing-box 隧道传输。
- MinIO API 继续只对服务端本机或内部容器网络开放，公网无法直接访问。
- 服务端状态中的内部端点固定指向实际内部服务，客户端传输描述独立且无 fallback 漂移。
- 旧 Protocol v1 profile 在兼容窗口内可继续同步；迁移后重新签发的 profile 不依赖 N1 专用名称。
- N1 与 `sync.970506.xyz` 部署之间迁移时，同一客户端任务无需手工修改存储地址。
- 客户端回滚后旧 profile 仍可恢复使用，不因移除新传输描述而丢失同步能力。

### 临时策略

在兼容迁移完成前不直接删除 `n1-minio.sfsc`，否则现有 SyncKey/profile 会立即失效。当前 UI 中该地址只能理解为 N1 隧道内部路由，不是用户配置或第三方公网端点。

`0.2.0-beta.2` 已将该内部端点从普通客户端远端目标摘要移除，并让服务端在加载持久状态时强制使用 `S3_ENDPOINT` 恢复 `internalEndpoint`，避免 N1 客户端别名继续污染服务端内部连接。为保持 Protocol v1 旧 SyncKey/profile 可用，本次不删除 `S3_CLIENT_ENDPOINT` 和 `extra_hosts` 兼容别名；新 profile 改为受管本地转发、停止携带该别名的完整迁移仍按上述步骤进入后续版本。

## SFSC-BETA-STORAGE-001：MinIO 容量不足被显示为同步冲突

- 严重级别：P1（阻断核心上传路径且错误原因被遮蔽）
- 状态：N1 SSD 迁移和 `storage_full` 映射已完成，容量预检与告警待后续运维增强
- 发现日期：2026-07-13
- 影响范围：N1 MinIO 部署、服务容量监控、rclone 错误归一化、客户端失败提示和试用门禁

### 现场根因

- 诊断包中的 rclone 日志明确返回 HTTP `507`、`XMinioStorageFull`，第三次重试结束时仍有 3599 个对象上传失败。
- N1 当前把 `/opt/sfsc-test/server/data/minio` 放在系统 eMMC 根分区；该分区总计 `6.5 GiB`、已用约 `6.3 GiB`、只剩约 `36 MiB`。
- 本轮 `home-sync/devices/test1` 已占用约 `3.9 GiB`，待上传数据总量约 `5.484 GiB`，系统盘从容量上不可能容纳完整数据和操作系统安全余量。
- N1 已挂载 `/ssd`，容量约 `219 GiB`、空闲约 `201.6 GiB`，但当前 MinIO bind mount 没有使用该 SSD。
- 客户端只保存了 `rclone_sync_failed` 和退出码 `1`，没有把 `507/XMinioStorageFull` 归一化为稳定错误；同时伪冲突提示优先显示，导致用户被引导去处理不存在的双向冲突。

### 立即恢复方案

1. 停止向当前 N1 MinIO 继续上传，避免系统盘完全耗尽并影响其他服务。
2. 将 MinIO 数据从系统盘无损迁移到 SSD 专用目录，并在 N1 compose 中使用明确、可审计的 SSD bind mount。
3. 迁移期间停止 MinIO 写入；复制完成后校验对象元数据数量、数据量和 MinIO bucket 可读性，再切换挂载。
4. 新 MinIO 启动并完成读写冒烟后才删除系统盘旧副本；删除前保留回滚点和迁移报告。
5. 确认系统盘恢复安全余量、`home-sync` 对象可读、`test1` 前缀存在后，再从客户端重新执行普通 copy 上传。rclone 应跳过已成功对象并补传失败对象。

### 产品修复步骤

1. N1 部署审计检查 MinIO 数据目录所在文件系统，禁止把试用对象存储放在容量不足的系统盘。
2. 服务端健康和管理摘要增加对象存储总容量、可用容量、使用率和 MinIO 最低空闲阈值状态，不再只显示 bucket 对象用量。
3. 同步开始前执行服务端容量预检；已知待上传量大于安全可用容量时应在传输前拒绝，并返回稳定 `storage_capacity_insufficient`。
4. 客户端从 rclone 错误摘要识别 `507/XMinioStorageFull`，归一化为稳定 `storage_full`，保留脱敏服务端错误摘要。
5. UI 优先显示“服务器存储空间不足”，给出联系管理员扩容或清理目标空间的建议；不得显示冲突处理提示。
6. 服务端容量进入警戒线时产生运维告警，并阻止创建会进一步扩大风险的试用任务。
7. 诊断包保留容量状态、稳定错误码、失败对象数量和日志截断信息，但不包含对象名称、存储密钥或内部路径。

### 验收标准

- N1 MinIO 使用 SSD 数据目录，系统盘保持足够安全余量。
- 迁移前后的 bucket、对象元数据数量和抽样对象读取校验一致，并完成回滚演练。
- 模拟 MinIO `507/XMinioStorageFull` 时，客户端显示 `storage_full`，不显示同步冲突。
- 容量不足可以在上传开始前被预检拦截；预检和实际写入竞态仍由 507 错误兜底。
- 扩容后重新执行普通上传可补齐之前失败的 3599 个对象并以退出码 0 完成。
- 服务端控制台能够看到总容量、可用容量、使用率和告警状态。
